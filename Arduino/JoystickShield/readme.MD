# طرح ارتباط Joystick Shield با nRF24L01+

> وضعیت این سند: پیشنهاد طراحی برای بازبینی. در این مرحله هیچ تغییری در کد فرستنده یا گیرنده اعمال نشده است.

## 1. هدف و فرض‌ها

فرستنده از Arduino Nano، شیلد Funduino Joystick Shield v1.A، یک جوی‌استیک اضافه و nRF24L01+ تشکیل می‌شود. وضعیت ورودی‌ها باید بدون `delay()` نمونه‌برداری شود و حداکثر در بازه‌های 50 میلی‌ثانیه به گیرنده برسد. وقتی ورودی تغییر نکرده است، ارسال state جدید لازم نیست؛ بااین‌حال Heartbeat لازم برای تشخیص اتصال و سنجش کیفیت لینک هر 50 میلی‌ثانیه ادامه دارد.

منظور از «غیربلوکی» در این طراحی این است که زمان‌بندی برنامه با `millis()`/تایمر انجام شود و هیچ `delay()` در `loop()` نباشد. باید توجه داشت که `RF24::write()` کاملاً asynchronous نیست و تا دریافت ACK یا تمام‌شدن retryها منتظر می‌ماند. اگر توقف چند میلی‌ثانیه‌ای هم غیرقابل‌قبول باشد، نسخهٔ نهایی باید از `startFastWrite()` به‌همراه IRQ و یک state machine استفاده کند. برای دورهٔ 50 ms، `write()` با retry محدود معمولاً ساده‌تر و مطمئن‌تر است، به شرط اینکه بیشینهٔ زمان آن اندازه‌گیری و محدود شود.

## 2. بررسی پایه‌ها و اتصالات

پایه‌های استفاده‌شده در `JoystickShield.ino` با نقشهٔ رایج Shield v1.A به صورت زیر است:

| کارکرد | پایه Nano | نتیجه |
|---|---:|---|
| دکمه‌های A تا F | D2 تا D7 | بدون تداخل |
| محورهای جوی‌استیک روی شیلد | A0، A1 | بدون تداخل |
| کلید جوی‌استیک روی شیلد | A2 | بدون تداخل |
| محورهای جوی‌استیک اضافه | A3، A4 | بدون تداخل |
| کلید جوی‌استیک اضافه | A5 | بدون تداخل |
| nRF24 CE | D9 | بدون تداخل |
| nRF24 CSN/SS | D10 | بدون تداخل |
| nRF24 MOSI | D11 (SPI) | صحیح |
| nRF24 MISO | D12 (SPI) | صحیح |
| nRF24 SCK | D13 (SPI) | صحیح |

بنابراین در تخصیص پایه‌های فعلی تداخل دیجیتال/آنالوگ یا SPI دیده نمی‌شود. بااین‌حال موارد زیر باید روی سخت‌افزار واقعی کنترل شوند:

1. **تغذیه nRF24 فقط 3.3V باشد، نه 5V.** زمین Nano، شیلد، جوی‌استیک دوم و رادیو مشترک باشد.
2. یک خازن بای‌پس نزدیک پایه‌های VCC/GND ماژول قرار گیرد؛ شروع مناسب `100 nF` سرامیکی موازی با `10 µF` است. برای ماژول PA/LNA بهتر است رگولاتور 3.3V مستقل با جریان کافی استفاده شود؛ خروجی 3.3V برد Nano ممکن است برای پیک جریان این مدل مناسب نباشد.
3. سیم‌های SPI و تغذیه کوتاه باشند. آنتن از Nano، کابل USB و سیم‌های جوی‌استیک فاصله داشته باشد.
4. ورودی‌های منطقی nRF24 عموماً با خروجی 5V میکروکنترلر استفاده می‌شوند، اما VCC ماژول همچنان باید 3.3V باشد. اگر برد/کلون خاصی استفاده شده، مشخصات همان ماژول نیز بررسی شود.
5. `RF24_PA_HIGH` برای تست رومیزی و فاصلهٔ کم ممکن است اشباع یا مشکل تغذیه ایجاد کند. آزمایش از `RF24_PA_LOW` شروع شود و فقط در صورت نیاز افزایش یابد.
6. A4 و A5 در این طرح ورودی آنالوگ‌اند؛ در نتیجه I²C هم‌زمان قابل استفاده نیست. این تداخل در کد فعلی وجود ندارد، ولی برای توسعهٔ آینده مهم است.

این بررسی صرفاً از روی کد و تصویر pinout داخل پروژه است. تأیید نهایی به continuity test و مشاهدهٔ ولتاژ 3.3V هنگام ارسال نیاز دارد.

## 3. ایرادها و محدودیت‌های کد فعلی

- `Pad pad;` پیش از تعریف کامل کلاس `Pad` آمده است و در C++ معمول Arduino قابل ساخت نیست؛ شیء باید بعد از تعریف کلاس ایجاد شود.
- `delay(10)` هنگام کالیبراسیون و `delay(20)` در `loop()` وجود دارد. اولی فقط هنگام راه‌اندازی است، ولی دومی شرط غیربلوکی‌بودن را نقض می‌کند.
- `Joystick::changed()` تغییر نسبت به آخرین state ارسال‌شده را نمی‌سنجد؛ هر زمان محور بیرون deadzone باشد `true` می‌ماند و ارسال در هر loop تکرار می‌شود.
- هیچ محدودیت 50 ms وجود ندارد؛ نرخ ارسال فعلی تقریباً به `delay(20)` و زمان `radio.write()` وابسته است.
- کلیدها debounce ندارند و ممکن است یک فشار چند تغییر کاذب بسازد.
- رویدادهای 0/1/2/3 برای دکمه‌ها با snapshot وضعیت مخلوط شده‌اند. برای ارتباط مقاوم، bitmask وضعیت فعلی همراه sequence number بهتر است؛ edge را گیرنده از دو snapshot متوالی استخراج می‌کند.
- مرکز جوی‌استیک تنها از یک نمونه تعیین می‌شود. بهتر است هنگام startup چند نمونهٔ پایدار گرفته، میانگین/میانه محاسبه و نتیجه اعتبارسنجی شود.
- ساختار خام C++ فاقد version، نوع پیام، sequence، شناسهٔ pair و کنترل replay است.
- آدرس ثابت `"00001"` عمومی است و pair شدن یا امنیت ایجاد نمی‌کند.
- نتیجهٔ `radio.begin()` و `radio.write()` بررسی نمی‌شود و recovery برای خرابی رادیو وجود ندارد.
- فرستنده و گیرنده payload را با initializerهای متفاوت تعریف کرده‌اند. packed بودن اندازه را در AVR فعلاً یکسان می‌کند، ولی باید `static_assert` و serialization صریح اضافه شود.

## 4. نمونه‌برداری، deadzone و تشخیص تغییر

### زمان‌بندی پیشنهادی

- اسکن ورودی‌ها: هر 2 تا 5 ms با مقایسهٔ تفاضلی `millis()` یا timer tick.
- debounce دکمه‌ها: هر تغییر خام فقط پس از 15 تا 25 ms پایداری پذیرفته شود؛ هیچ توقفی در loop رخ ندهد.
- slot رادیویی: هر 50 ms (`20 Hz`) با محاسبهٔ deadline به صورت تفاضلی و امن در برابر overflow.
- timeout گیرنده: پس از 150 تا 250 ms بدون packet حالت link-lost و خروجی‌ها safe/neutral شوند.

### جوی‌استیک

1. در startup، وقتی دسته رهاست، برای هر محور چند نمونه گرفته و مرکز محاسبه شود.
2. نویز با فیلتر سبک مانند EMA یا median-of-3 کم شود.
3. deadzone نسبت به مرکز اعمال شود، نه نسبت به عدد ثابت 512.
4. برای جلوگیری از لرزش لبه، hysteresis به کار رود؛ برای مثال ورود به حرکت در `±20` و برگشت به صفر در `±14`.
5. خروجی پس از deadzone به بازهٔ مشخص (مثلاً `-512..511`) clamp/scale شود.
6. state فیلترشده با **آخرین state موفق ارسال‌شده** مقایسه شود. برای محور می‌توان threshold تغییر 2 تا 4 count یا quantization تعریف کرد تا نویز ارسال نسازد.

اگر state تغییر کند، flag مربوط در slot بعدی ارسال می‌شود. برای کنترل‌هایی که از دست‌دادن edge آن‌ها خطرناک است، state جاری تا دریافت ACK حداقل یک بار نگه داشته می‌شود؛ sequence number مانع اجرای دوباره می‌شود.

## 5. پروتکل ارتباطی پیشنهادی

nRF24 حداکثر payload برابر 32 بایت دارد. قالب پیشنهادی زیر fixed-size و مستقل از alignment کامپایلر است و باید byte-by-byte serialize شود:

| فیلد | اندازه | توضیح |
|---|---:|---|
| `magic` | 1 | مقدار ثابت برای ردکردن دادهٔ نامعتبر |
| `version_type` | 1 | 4 بیت نسخه + 4 بیت نوع پیام |
| `flags` | 1 | `STATE_CHANGED`, `PAIRED`, `ACK_REQUEST` و ... |
| `pair_id` | 4 | شناسهٔ غیرمحرمانهٔ رابطهٔ pair |
| `session_id` | 2 | مقدار تصادفی جدید در هر boot/session |
| `sequence` | 2 | شمارندهٔ packet با wrap-around |
| `buttons` | 1 | bitmask شش دکمه + SW1 + SW2 |
| `x1,y1,x2,y2` | 8 | چهار `int16_t` با ترتیب بایت مشخص little-endian |
| `changed_mask` | 1 | مشخص می‌کند کدام گروه ورودی تغییر کرده است |
| `reserved/status` | 2 | نسخهٔ باتری/status آینده؛ فعلاً صفر |
| `auth_tag` | 8 | MAC کوتاه‌شده برای اصالت و صحت پیام |
| **جمع** | **30 بایت** | زیر سقف 32 بایت |

نوع‌های پیام پیشنهادی:

- `DATA_HEARTBEAT`: هر 50 ms ارسال می‌شود. اگر ورودی عوض نشده باشد `STATE_CHANGED=0` است؛ همچنان می‌توان snapshot کامل را برای self-healing فرستاد.
- `PAIR_REQUEST`, `PAIR_CHALLENGE`, `PAIR_CONFIRM`: فقط در حالت pairing.
- `RESYNC`: برای شروع session جدید یا درخواست snapshot قطعی.

ارسال snapshot کامل در هر Heartbeat، با وجود اینکه ورودی تغییر نکرده، 9 بایت state ثابت دارد ولی مزیت مهمی دارد: اگر یک edge یا packet از دست برود، گیرنده حداکثر 50 ms بعد خودکار همگام می‌شود. اگر کاهش airtime/مصرف اولویت مطلق باشد، می‌توان heartbeat کوتاه و DATA متغیر داشت؛ ولی پیچیدگی dynamic payload و resync بیشتر می‌شود. برای این پروژه fixed 30-byte heartbeat انتخاب مطمئن‌تری است.

CRC شانزده‌بیتی داخلی nRF24 برای خطای تصادفی باقی می‌ماند؛ `auth_tag` جای CRC نیست و برای تشخیص فرستندهٔ مجاز و جلوگیری از جعل است.

## 6. کیفیت لینک: PDR، نه RSSI واقعی

nRF24L01+ RSSI عددی ندارد. بیت RPD فقط می‌گوید توان دریافتی تقریباً بالاتر یا پایین‌تر از آستانهٔ حدود `-64 dBm` بوده و برای نمایش درصد دقیق سیگنال مناسب نیست. بنابراین شاخص اصلی باید **Packet Delivery Ratio (PDR)** مبتنی بر Auto-ACK باشد.

### الگوریتم فرستنده

- هر 50 ms یک `DATA_HEARTBEAT` با Auto-ACK ارسال شود؛ packet تست جدا لازم نیست.
- نتیجهٔ `radio.write()` یک sample است: ACK دریافت شد = 1، timeout پس از retry = 0.
- یک ring buffer بیست‌بیتی نگه داشته شود؛ هر sample جدید جای قدیمی‌ترین sample را می‌گیرد.
- `quality_tx = 100 * successful / valid_samples`؛ پس از پرشدن پنجره، دقیقاً کیفیت یک ثانیهٔ اخیر را نشان می‌دهد.
- علاوه بر درصد، `consecutive_failures` و سن آخرین ACK نگه داشته شود. درصد به‌تنهایی برای تشخیص قطع فوری کافی نیست.
- retryهای داخلی نیز به صورت diagnostics ثبت شوند؛ موفقیت پس از چند retry همچنان delivered است، ولی میانگین retry می‌تواند اخطار زودتر دربارهٔ افت لینک بدهد.

### الگوریتم گیرنده و بازگرداندن کیفیت

- گیرنده از sequenceها تعداد packet دریافت‌شده/گمشده را در پنجره محاسبه می‌کند.
- گیرنده یک ACK payload کوچک شامل `acked_sequence`، `receiver_window_pdr`، flagهای وضعیت و MAC آماده می‌کند. ACK payload ذاتاً پاسخ packet بعدی است و ممکن است یک packet تأخیر داشته باشد.
- فرستنده کیفیت محلی خود را از نتیجهٔ ACK محاسبه می‌کند؛ عدد گیرنده صرفاً برای telemetry/نمایش و cross-check است.
- گیرنده چون فقط دریافت‌کننده است، کیفیت لینک را از فاصلهٔ sequenceها و timeout می‌سنجد. برای سنجش واقعی مسیر برگشت مستقل، باید نقش‌های رادیویی دوره‌ای عوض شوند؛ برای کاربرد کنترل یک‌طرفه معمولاً ارزش پیچیدگی را ندارد.

پیشنهاد سطح نمایش:

| وضعیت | معیار پیشنهادی |
|---|---|
| عالی | PDR ≥ 95% و شکست متوالی صفر |
| خوب | 85% تا 94% |
| ضعیف | 60% تا 84% یا چند retry مکرر |
| بحرانی | کمتر از 60% یا 3 شکست متوالی |
| قطع | بیش از 200 ms بدون packet/ACK معتبر |

مرزها باید پس از تست میدانی تنظیم شوند. عبارت «قدرت سیگنال» در UI بهتر است «کیفیت لینک» نامیده شود، چون این عدد PDR است، نه dBm.

## 7. Pairing، احراز اصالت و جلوگیری از پاسخ به دستگاه مشابه

فقط استفاده از channel یا آدرس 5 بایتی nRF24 امنیت نیست؛ هر دستگاهی که آن‌ها را بداند می‌تواند packet بفرستد. nRF24L01+ رمزنگاری داخلی ندارد. طراحی پیشنهادی دو سطح دارد:

### Pairing اولیه

1. هر دو دستگاه تنها با نگه‌داشتن دکمهٔ فیزیکی/ترکیب مشخص هنگام روشن‌شدن، برای 30 تا 60 ثانیه وارد Pairing Mode شوند. pairing از راه دور در حالت عادی پذیرفته نشود.
2. هر دستگاه `device_id` تصادفی و یک nonce تازه تولید کند. ATmega328P مولد تصادفی امن داخلی ندارد؛ seed صرفاً از `analogRead()` کافی نیست. بهترین روش provisioning یک کلید تصادفی روی PC هنگام پروگرام و ذخیره در EEPROM است.
3. گیرنده `PAIR_REQUEST(sender_id, nonce_T)` را می‌گیرد و `PAIR_CHALLENGE(receiver_id, nonce_R)` می‌فرستد.
4. فرستنده `PAIR_CONFIRM` شامل هر دو ID، هر دو nonce و MAC را می‌فرستد. گیرنده فقط MAC معتبر و nonce جاری را می‌پذیرد.
5. هر دو سمت `pair_id`، آدرس رادیویی اختصاصی مشتق‌شده و کلید لینک را در EEPROM همراه version و CRC ذخیره می‌کنند.
6. پس از pair، از آدرس discovery عمومی خارج و به آدرس 5 بایتی اختصاصی می‌روند. Pairing Mode بسته می‌شود.

### کلید و MAC

- گزینهٔ best practice: یک secret منحصربه‌فرد از پیش provisioning‌شده برای هر کیت/دستگاه، سپس مشتق‌کردن link key از secret و nonceهای دو طرف.
- اگر دستگاه‌ها هیچ secret یا روش out-of-band مشترک ندارند، pairing رادیویی به‌تنهایی در برابر مهاجم فعال امن نیست. دکمهٔ فیزیکی، زمان کوتاه و فاصلهٔ نزدیک فقط ریسک را کم می‌کند و امنیت cryptographic کامل نمی‌سازد.
- برای AVR می‌توان AES-CMAC با کلید 128 بیتی یا یک MAC سبک و بررسی‌شده مانند SipHash-2-4 با کلید 128 بیتی و tag 64 بیتی استفاده کرد. الگوریتم دست‌ساز، XOR یا CRC به‌عنوان authentication پذیرفته نیست.
- کلید هرگز روی هوا ارسال نشود و در log چاپ نشود. در unpair، رکورد EEPROM پاک/نامعتبر شود.

### هر packet عادی

- گیرنده ابتدا آدرس رادیویی، سپس `pair_id`، نسخه، `session_id`، sequence و در آخر `auth_tag` را بررسی کند.
- MAC باید تمام header و payload (و جهت TX→RX یا RX→TX) را پوشش دهد تا packet یا ACK یک جهت در جهت دیگر replay نشود.
- برای هر session فقط sequence جدید در یک replay window کوچک پذیرفته شود. packet تکراری ممکن است ACK شود، ولی state دوباره اجرا نشود.
- session جدید با nonce تصادفی و یک پیام authenticated آغاز شود. ذخیره‌کردن counter بلندمدت در EEPROM در هر packet مناسب نیست، چون عمر EEPROM را کم می‌کند؛ session nonce این نیاز را کاهش می‌دهد.
- گیرنده به packet نامعتبر پاسخ کاربردی ندهد. Auto-ACK سخت‌افزاری پیش از بررسی MAC تولید می‌شود، بنابراین مهاجمِ دارای آدرس ممکن است ACK خام بگیرد؛ اما نباید state یا ACK payload معتبر دریافت کند. اگر پنهان‌سازی حضور نیز الزام امنیتی است، nRF24 به‌تنهایی انتخاب مناسبی نیست.

آدرس اختصاصی احتمال برخورد اتفاقی را بسیار کم می‌کند؛ MAC است که مانع کنترل توسط فرستندهٔ مشابه یا جعلی می‌شود.

## 8. state machine پیشنهادی

فرستنده:

`BOOT/CALIBRATE → LOAD_PAIR → SESSION_SYNC → CONNECTED ↔ DEGRADED → LOST`

- در همهٔ حالت‌ها loop زنده می‌ماند و ورودی‌ها اسکن می‌شوند.
- در `CONNECTED/DEGRADED` هر deadline پنجاه‌میلی‌ثانیه‌ای heartbeat فرستاده می‌شود.
- در `LOST` heartbeat با backoff محدود ادامه پیدا می‌کند تا اتصال برگردد؛ state تازه باید پس از reconnect به صورت snapshot ارسال شود.
- Pairing فقط از `PAIRING` فیزیکی و زمان‌دار قابل ورود است.

گیرنده:

`BOOT → LOAD_PAIR → LISTEN → VALIDATE → APPLY_STATE` و در timeout وارد `FAILSAFE` می‌شود. فقط packet دارای MAC و sequence معتبر watchdog ارتباط را refresh می‌کند؛ دریافت noise یا packet pair دیگر نباید از failsafe جلوگیری کند.

## 9. تنظیمات اولیهٔ رادیو

- Address width: پنج بایت.
- CRC: شانزده‌بیتی.
- Auto-ACK: روشن.
- Dynamic payload/ACK payload: روشن، اگر ACK telemetry استفاده شود.
- Data rate: `250 kbps` برای برد/حساسیت بهتر، با تست واقعی محیط.
- Channel: مقدار 108 فعلی (2508 MHz) از Wi-Fi 2.4 GHz دورتر است، اما channel باید با scan/تست محل انتخاب شود و محدودیت‌های مقرراتی منطقه رعایت شود.
- Retry delay/count: طوری انتخاب شود که بدترین زمان یک slot از 50 ms بیشتر نشود. تنظیم فعلی `setRetries(5,15)` می‌تواند تقریباً ده‌ها میلی‌ثانیه زمان انتظار بسازد و باید با analyzer/`micros()` اندازه‌گیری شود. شروع محافظه‌کارانه، retry کمتر و jitter کوچک بین دستگاه‌هاست.
- در setup، نتیجهٔ `radio.begin()` و `isChipConnected()` بررسی شود و configuration دو سمت دقیقاً یکسان باشد.

## 10. معیار پذیرش پیاده‌سازی آینده

1. هیچ `delay()` در loop یا مسیر runtime نباشد.
2. نرخ heartbeat برابر 20 Hz با jitter اندازه‌گیری‌شده و محدود باشد.
3. state بدون تغییر باعث تغییر flag/data event نشود، ولی heartbeat و سنجش کیفیت ادامه یابد.
4. deadzone، hysteresis، debounce و threshold تغییر با تست ثبت‌شده کار کنند.
5. با حذف یک یا چند packet، snapshot بعدی گیرنده را self-heal کند.
6. گیرنده حداکثر پس از timeout تعیین‌شده وارد failsafe شود.
7. کیفیت پنجرهٔ لغزان با الگوهای مصنوعی 20/20، 15/20 و 0/20 به ترتیب 100%، 75% و 0% بدهد.
8. packet از pair دیگر، MAC خراب، sequence تکراری یا session قدیمی اعمال نشود.
9. قطع برق هر طرف، wrap شدن `millis()` و wrap شدن sequence تست شود.
10. اندازهٔ payload با `static_assert` حداکثر 32 بایت و serialization در هر دو سمت یکسان باشد.
11. تست نزدیک با PA_LOW و تست فاصله/نویز انجام و جریان/ولتاژ 3.3V هنگام TX بررسی شود.

## 11. تصمیم‌های لازم پیش از پیاده‌سازی

- تعریف دقیق «غیربلوکی»: حذف `delay()` کافی است یا حتی توقف محدود `radio.write()` نیز ممنوع است؟
- نوع ماژول: nRF24L01+ معمولی یا PA/LNA، و منبع دقیق 3.3V چیست؟
- رفتار failsafe خروجی گیرنده چیست؟ صفرکردن محورها، رهاکردن همهٔ دکمه‌ها یا حفظ آخرین state؟ پیشنهاد ایمن: neutral/released.
- آیا امنیت در برابر مزاحم فعال لازم است یا صرفاً جلوگیری از pair اشتباهی؟ پیشنهاد این سند authentication واقعی با کلید provisioning‌شده است.
- آیا نمایش کیفیت فقط در فرستنده لازم است یا باید به گیرنده/نمایشگر دیگری نیز تحویل شود؟
